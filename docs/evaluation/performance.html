Performance

Scope: the API and its database access, the live-update path, the extension popup and service worker, and the mobile app. Method: static review of every hot path against Marten, Npgsql, Chrome and Flutter behaviour, plus measurements where they could be taken without a running database (extension bundle sizes and test timings). Database numbers are estimates until an EXPLAIN ANALYZE on a seeded table confirms them; they are marked as such.

Verdict

Nothing is slow today, and the design choices that matter at scale are mostly right: UUIDv7 ids make the feed an append-only index, cursor paging never uses OFFSET, the inline snapshot means reads never replay events, the NOTIFY payload carries only ids, the fan-out channels are bounded, and the extension bundles are tiny. The problems are the ones that only show up with volume: both clients persist their entire loaded feed on every change, the mobile app re-parses that cache on every event, the list query has no index that matches it, and the event store grows forever. All are cheap to fix now and expensive to fix after there is data.

Score: 3 / 5 today, trending to 2 / 5 at a few thousand packets per user without the fixes below.

Findings

Ordered by impact. "When it bites" gives the data volume or concurrency at which the problem becomes visible.

  1. Mobile re-serialises and re-parses the whole feed on every change (High). _persist in packets_provider.dart runs after every state change (nine call sites: build, refresh, load more, push, live create, live delete, hide, unhide, sync) and does two things: PacketCache.save encodes every loaded packet, all pages ever loaded, into one shared_preferences string, then ref.invalidate(hasCachedPacketsProvider) re-reads and fully re-parses that string only to answer isNotEmpty. All of it runs on the UI isolate, and on Android the platform rewrites the whole preferences XML file per commit, with every quote escaped. One local delete is two full cycles (hide, then the echoed delete event). When it bites: fine at one page; roughly 10 to 30 ms of jank per event at 1,000 packets; 100 ms and ANR risk on pause with 64 KB bodies. Fix: cache only the first page and its cursor (the cache exists to show something instantly; older pages are refetched by load-more anyway), replace the invalidation with an in-memory flag, and debounce writes by about 300 ms so bursts write once. Isolate.run for the encode would hide the jank but not the file churn; a database would be right only if large bodies had to be cached.

  2. The extension cache is unbounded and the popup rebuilds, animates and layout-thrashes every cached tile on every open (High). FeedStore.commit in feed.ts saves the full list to chrome.storage.local on every commit and loadMore keeps appending, so the cache grows by 50 per scroll-to-end and is never trimmed. On every open renderFeed builds a tile for every cached packet, .packet has a slide-in animation so all of them animate at once, and measureClampedTiles interleaves a layout read (scrollHeight) with a write (classList.remove, body.after) per text tile, forcing one synchronous layout per tile. Without unlimitedStorage the cache hits the 10 MB quota at about 30,000 average packets or 160 maximum-size ones, after which every save fails silently and the stale cache is shown forever. When it bites: one page is a few milliseconds; 1,000 cached packets is 10,000 DOM nodes, 1,000 forced layouts and 1,000 simultaneous animations, hundreds of milliseconds to seconds on every open. Fix: cap the cache at the first page; split measureClampedTiles into a read loop then a write loop; animate only packets that arrive live; consider content-visibility: auto on .packet.

  3. No index serves the list query (High). Program.cs declares .Index(p => p.UserId), which Marten creates as an expression index on (data ->> 'UserId'), and GetPackets.cs runs where data ->> 'UserId' = $1 and id < $2 order by id desc limit 51. PostgreSQL has two single-column paths and no composite one: scan the user's expression index and sort every one of their rows per page, or walk the primary key backwards filtering every user's rows until 51 of this user's turn up. The planner chooses by statistics, so a heavy user pays a full scan of their rows on every page and a misestimate with many users visits roughly 51 times the user count. When it bites: below about 5,000 packets per user both plans are a few milliseconds; a user with 100,000 packets pays 100 to 300 ms warm per page. Fix: one composite computed index, .Index([p => p.UserId, p => p.Id]), which turns the query into a bounded backward range scan of 51 entries regardless of table size. Verify the DDL Marten emits uses the id column for the identity member; if it emits (data ->> 'Id') instead, use .Duplicate(p => p.UserId) and a Weasel index over user_id, id. The single-column index becomes redundant.

  4. Live-update dispatch is serial, one query per notification (Medium). PacketNotificationListener.DispatchAsync opens a query session and loads one aggregate per Created notification, sequentially, so every queued notification waits for the ones before it and a slow query stalls live updates for everyone on the instance. When it bites: throughput caps at one database round trip per notification per instance (hundreds per second), far above human send rates, so in practice it is latency under bursts. Fix: per wake-up, collect the ids whose users have subscribers and load them with one LoadManyAsync, then publish per user in arrival order.

  5. Reconnect and resync storms (Medium). Both clients use base × (0.75 + random × 0.25) backoff, so after a server restart (every stream ends on ApplicationStopping) all clients reconnect within a 250 ms window, and every connection's first resync triggers an immediate GET /api/packets. When the LISTEN connection drops, PublishToAll(Resync) makes every open stream on the instance refetch at once, against the database that just recovered. When it bites: around 1,000 concurrent streams per instance, that is 1,000 list queries, JWT validations and TLS handshakes inside one second. Fix in both clients: full jitter (random × base) and a random 0 to 3 s delay before the resync fetch. Optionally send an SSE retry: value and spread PublishToAll over a few seconds.

  6. The event store grows forever (Medium). Deleting appends PacketDeleted and the inline projection removes the snapshot, but mt_events keeps both events and mt_streams keeps the stream; nothing archives, and UseArchivedStreamPartitioning is off. A 64 KB text body is stored twice while live and once forever after deletion. Rebuilding the snapshot replays every event ever written, deleted packets included. When it bites: 10,000 users sending 10 a day is about 36 million events and 20 to 40 GB a year plus indexes, vacuum and backups; at hundreds of users it is a non-issue for years. Fix: ArchiveStream in the delete handler in the same save, turn on archived-stream partitioning so queries and rebuilds skip them, and purge the archived partition after some days. The larger alternative is that packets don't need event sourcing at all (one document store and delete), which halves write volume; that is an architecture decision rather than a tuning fix and is discussed in Codebase Health.

  7. Four to six round trips per create and delete, and runtime code generation on first use (Medium). Create does FetchForWriting on a brand-new id (a batched select that can't find anything), SaveChangesAsync (begin, batch, commit), a pg_notify on a second connection, then FetchLatest to re-read an aggregate whose content the code already knows. Delete is LoadAsync, then a save in which the inline projection has to look up the stream itself, then notify. When it bites: latency only, 2 to 3 ms at 1 ms database round trip, 10 to 30 ms with a managed database in another zone. Fix: StartStream<PacketAggregate>(id, event) for create and return the aggregate built from the event; FetchForWriting plus AppendOne for delete, which also gives optimistic concurrency. Separately, Marten generates storage and projection code with Roslyn on first use after every start, typically one to three seconds of first-request latency per deploy and replica; mitigate with OptimizeArtifactWorkflow(TypeLoadMode.Static) and codegen write in the pipeline, and ApplyAllDatabaseChangesOnStartup() so replicas don't race the schema check.

  8. Mobile cold start waits for Google before showing the cached feed, and parses the cache twice (Medium). StartupRouter in app.dart shows a spinner until both the auth provider (Google Sign-In initialise plus a silent sign-in round trip) and the cache check complete, even though the feed page already handles "signed out with cache". The cache is parsed once by hasCachedPacketsProvider and again by PacketsNotifier.build. When it bites: every cold start, by seconds on a slow network. Fix: route to the feed as soon as the cache check completes and treat auth-pending as signed out; expose one cached-state provider that both the router and the notifier read.

  9. The SSE loop throws a TimeoutException per heartbeat per stream (Low). GetPacketEvents.WaitAsync ends each 20-second idle wait with a thrown and caught exception. At 10,000 idle streams that is 500 exceptions a second, one to three percent of a core. Fix: Task.WhenAny(waitToRead, Task.Delay(interval, ct)). Also exclude /api/packets/events from tracing in ServiceDefaults/Extensions.cs next to the health endpoints, since each stream otherwise keeps an Activity alive until it disconnects.

  10. Mobile list details (Low). packet_list.dart keys children by packet id but passes no findChildIndexCallback, so every insert at the top of the reversed list discards and rebuilds every visible tile's state (controllers, Dismissible, cards); about a millisecond per event today. AutomaticKeepAliveClientMixin on PacketList does nothing because the list sits in a Column, not a lazy viewport. The 60-second setState in PacketFeedPage only rebuilds the app bar because PacketList is const. Fix: add the callback over a per-build id-to-index map and delete the mixin.

  11. Mobile SSE and HTTP: no problems found. The 45-second idle timeout against a 20-second heartbeat, the cancel path with AbortableRequest, the shared http.Client, the de-duplicated token refresh and the backoff reset on resync all check out.

  12. Extension service-worker lifetime: assumptions hold (Low). The popup's 20-second port pings keep the worker inside Chrome's 30-second idle limit while the popup is open; the streaming fetch body does not keep the worker alive by itself, so if Chrome ever kills it the popup's onDisconnect reconnects after a second and the resync refetches the first page. Scheduled deletes are 4-second timers, inside the idle window. Document these assumptions in the extension doc so a future change doesn't break them silently.

Already good

  • UUIDv7 stream ids and Id < cursor paging with Take(51): O(page) per request once finding 3 is fixed.
  • Lightweight sessions, inline snapshots, request limits (256 KB body, 64 KB text, 2 KB URL).
  • NOTIFY carries ids only, HasSubscribers is checked before loading, one LISTEN connection per instance with a keep-alive, bounded per-subscriber channels that complete on overflow so the client resyncs instead of the server buffering, locks held only for dictionary operations, streams closed on shutdown.
  • SSE transport: heartbeat under the client timeouts, X-Accel-Buffering: no, and response compression leaves text/event-stream alone.
  • Extension: bundles under 15 KB, tiles cached by id and only re-inserted when the order changed, the stream exists only while a popup is open, deletes survive the popup closing.
  • Mobile: lazy ListView, one http.Client, de-duplicated silent refresh, a StreamTransformer SSE decoder so cancelling closes the socket immediately.

Steps forward

  1. Bound both caches to the first page, debounce the mobile write, drop the cache re-parse (S, mobile and extension). Fixes 1 and 2 and removes the quota cliff.
  2. Composite index and the round-trip fixes (S, API). Fixes 3 and 7; verify with EXPLAIN ANALYZE on a seeded table and keep the explain output in the repo as a test fixture or doc.
  3. Archive deleted streams and partition (S, API). Fixes 6 before there is data to migrate.
  4. Batch dispatch, full jitter, resync delay (S, API and clients). Fixes 4 and 5.
  5. Static code generation and startup schema application (S, API and pipeline). Part of 7; belongs with the deploy work.
  6. Mobile start-up routing and the list callback (S, mobile). Fixes 8 and 10.
  7. A load test (M): a k6 or NBomber script that signs in a few hundred synthetic users, holds streams open, and sends packets, run against a staging deployment before the first public release; it will confirm or correct every estimate above.
