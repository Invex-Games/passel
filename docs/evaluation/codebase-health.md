# Codebase Health

Scope: structure, duplication, test coverage, error handling, configuration, dependencies, dead code and the deployment story across the API, the extension, the mobile app and the Atom build. Method: every component was read in full, every build and test command was run (results in [Developer Experience](developer-experience.md)), and package freshness and vulnerability scans were taken.

Size for reference: API 1,638 lines of C# plus 511 of tests; Atom build 1,049; extension 1,971 lines of TypeScript plus 389 of tests; mobile 3,743 lines of Dart plus 2,810 of tests. Largest files: `popup.ts` 710, `packets_provider.dart` 552, `theme.dart` 386, `packet_list.dart` 360.

## Verdict

This is a small, strict and readable codebase with zero warning debt, fast green test suites, and the hard concurrency cases reasoned about in comments and tests. Its weaknesses are structural rather than local: the API's real behaviour (HTTP, auth, Marten, SQL, LISTEN/NOTIFY, SSE) has no automated coverage at all; the packet wire shape is declared four times in C# and hand-parsed twice in the clients with nothing detecting drift; the trickiest logic in the repository, the feed state machine, exists twice with only the author's memory keeping them in step; and there is no CI, no automated dependency updates and no deployment path. All of these are cheap while the codebase is this size.

Score: 3 / 5.

## Strengths

- Concurrency and failure modes are written down and tested: NOTIFY only after commit, with the reason it can't be queued in the session; bounded subscriber channels that complete instead of dropping; the hub subscribes before the first `resync`; heartbeat and idle timeouts aligned across server and both clients.
- Security-aware details throughout (404 for foreign ids, canonical-only id decoding, `http(s)`-only links on both sides, nonce and state checks, single-flight token refresh).
- Both clients tolerate unknown packet types and malformed events instead of failing the page.
- Strictness everywhere: `TreatWarningsAsErrors`, nullable, C# 14 extension members used tastefully, TypeScript `strict` and `isolatedModules`, Dart strict modes. Zero warnings in every suite.
- The tests that exist are behaviour tests with hand-written fakes and good names, and the whole loop runs in under ten seconds warm.
- Non-obvious code carries explanatory comments (`feed.ts`, `packets_provider.dart`, `build.mjs`).
- Pinned and locked dependencies (`package-lock.json` honoured with `npm ci`, `pubspec.lock` tracked, exact NuGet versions), and nothing vulnerable in any .NET project including transitives.

## Findings

Ordered by importance.

1. **The API's real behaviour has no automated coverage (High).** The 42 tests cover `Validate`, `Paginate`, `StreamPacketEvents`, the hub, notification parsing and id encoding, all pure helpers; the test project references only `xunit.v3`. Untested: `PacketStoreService` (Marten `FetchForWriting`, the inline snapshot, `ShouldDelete`), the cursor query over UUIDv7 ids, NOTIFY after commit through `LISTEN` to the hub to SSE, JSON polymorphism with out-of-order metadata, the development policy scheme, the request size limit. The testing guide admits it: "check those by running the AppHost". A Marten or Npgsql upgrade or a mapping change can break production silently, and the resync guarantee both clients rely on is unproven. Fix: an integration test project with `Testcontainers.PostgreSql` and `WebApplicationFactory<Program>` (`InternalsVisibleTo` is already declared), a test authentication scheme that reads the user id from a header, and tests for create-then-list and ownership isolation, paging over 51 packets with the returned cursor, delete semantics (204, then 404, other user 404), SSE end to end (open the stream with `ResponseHeadersRead`, create, assert `resync` then `packet-created`, which exercises `pg_notify` and the listener for real), and schema creation from an empty database. `Aspire.Hosting.Testing` is closest to production but starts the extension build and the tunnel too; keep it for one optional smoke test. Wire the new project into `atom TestWebApi`.

2. **The packet wire model is declared four times and hand-parsed twice, with nothing detecting drift (High).** The domain union `Packet` in `PacketAggregate.cs`, `PostPacketRequestBody` and `PostPacketResponseBody` in `PostPacket.cs`, and `GetPacketsResponseBody.Packet` in `GetPackets.cs`; the last two are field-for-field identical and mapped twice. Each client re-encodes the `$type`, `name|title|fileName` and `url|body|parcelId` mapping on its own (`packets.ts`, `packet.dart`). OpenAPI exists only at runtime in Development and is never exported. Adding `CreatedAt` today means four C# edits, two client edits and three test suites, and no test fails if one is missed. Options:
   - Shared contracts with generated clients (Kiota for TypeScript and Dart, or openapi-generator): best typing, but the `$type` union maps to `oneOf` plus `discriminator`, where Dart generators are weakest, and it adds a code-generation step to two toolchains for five endpoints.
   - Hand-written clients plus contract fixtures: cheap, and catches drift in all three suites.
   - Committed OpenAPI as documentation only: no enforcement.
   - Recommendation: the fixtures now, generation if the API grows past a handful of endpoints. Collapse the C# declarations to one response DTO used by create, list and SSE with one mapper; export the OpenAPI document at build (`Microsoft.Extensions.ApiDescription.Server`) and commit it under `docs/reference/` with a test that fails when it is stale; write `contracts/fixtures/` (one JSON file per `$type`, a page, the three SSE payloads) from a C# test using the real `JsonOptions`, and make `packets.test.ts` and `packet_test.dart` parse those files.

3. **The feed state machine is implemented twice with identical invariants and nothing enforcing parity (High).** `FeedStore` in `feed.ts` and `PacketsNotifier` in `packets_provider.dart` share generation, fetch sequence, arrivals, deleted ids, hidden map, the reconcile step and the `syncLatest` overlap rule; the Dart one adds an auth epoch and loading-state branches. The tests mirror by name (18 TypeScript cases, 37 Dart). A bug fixed in one is not necessarily fixed in the other, and this is the code most likely to regress under a small change. Sharing code across TypeScript and Dart is not sane. Fix: make parity executable with a language-neutral scenario file (`contracts/feed-scenarios.json`: a list of operations such as `showCached`, `refresh:start`, `refresh:resolve`, `applyCreated`, `applyDeleted`, `hide`, `unhide`, `loadMore:resolve`, each with the expected id list afterwards) and a 60-line interpreter in each suite; both suites already use a hand-resolved fake source and an in-memory cache. Separately, if the SSE stream carried event ids or the list endpoint took `?since=`, clients could replay instead of reconciling in-flight fetches, which shrinks both machines; consider it with the storage-model decision below. Document the invariants once ([Developer Experience](developer-experience.md), finding 9).

4. **Error handling is consistent on the server and lost on the mobile client (Medium).** The API uses ProblemDetails and field-keyed validation problems; the extension's `readError` turns title, detail and errors into one sentence and maps network failures to a friendly message, with three remaining raw `Error: …` sites in `popup.ts`. The mobile `validateResponse` never reads the body (`throw Exception('$context failed with HTTP …')`), so a 400 the server carefully composed is discarded, and the UI shows `'Push failed: $e'`, `'Refresh failed: $e'`, `'Couldn't delete packet: $e'`, `asyncState.error.toString()`, `e.toString()` and `'Auth error: …'`. Fix: parse `application/problem+json` into an `ApiException` with status, title, detail and field errors (mirroring `api.ts`), wrap socket and timeout errors into a `NetworkException`, map both to copy in one `describeError` used by every snackbar, and add Dart tests mirroring the extension's `readError` cases.

5. **Dead and speculative code (Medium).** `Domain/Commands/CreateFilePacket.cs` has no references. The `File` packet exists in six C# declarations and both clients while the API rejects creating one, which the docs then have to explain as "returned only". `EndpointBuilderExtensions.cs` defines thirteen helpers of which only `AcceptsJson` is used. `IFlutterHelper.cs` contains two unexplained `Task.Delay(2000)` calls. Fix: delete the unused command and helpers; since no production data can contain a `File` packet, remove it end to end and reintroduce it with parcels; replace the sleeps with the condition they wait for.

6. **Google client ids live in six places under four naming schemes (Medium).** AppHost parameters (`google-client-id`, `google-client-secret`, `google-extension-client-id`) in user secrets; the extension's `.env` (`GOOGLE_CLIENT_ID`); the mobile `.env` (`SERVER_CLIENT_ID`, `APP_CLIENT_ID`); `_atom/appsettings.json` (`server-client-id`, `mobile-app-client-id`, with Key Vault secret names as placeholder values); a git-ignored `_atom/appsettings.Development.json`; and the API's git-ignored `appsettings.Development.json`. The web client id alone has four names. The local extension `.env` on this machine has already drifted (it carries variables `build.mjs` never reads). Fix: make the AppHost user secrets the single development source, add a sync step to `SetupDevEnvironment` that writes both `.env` files from them (plus the stable tunnel URL), use one vocabulary everywhere (`GOOGLE_WEB_CLIENT_ID`, `GOOGLE_WEB_CLIENT_SECRET`, `GOOGLE_EXTENSION_CLIENT_ID`, `GOOGLE_ANDROID_CLIENT_ID`), rename the Atom parameters to match, and drop the placeholder strings so "not configured" is explicit.

7. **Dependency hygiene: well pinned, not automated, build tooling drifting (Medium).** No `Directory.Packages.props` (OpenTelemetry and JetBrains versions repeated across projects), no SDK pin in `global.json`, no Node pin, no Renovate or Dependabot, no CI. `_atom` is on Invex.Atom 3.7.0 while the global tool is 4.2.0 and 5.0.0 is current. Pending majors: TypeScript 7, vitest 5 (which also clears the four dev-only advisories), `flutter_riverpod` 3, `share_plus` 13, `dynamic_color` 2; Aspire 13.6.3 is a patch away. Atom can generate the missing automation: the `Invex.Atom.Module.GithubWorkflows` package (present in the NuGet cache, not referenced) exposes workflow and Dependabot definitions, and `Invex.RepoUtils` has a DocFX publish step; exact usage unverified. Fix: central package management, `global.json` with `rollForward: latestFeature`, `engines` in `package.json`, the workflows module with `Test` on pull requests and `Build*` plus docs publish on `main`, a Dependabot definition for NuGet, npm, pub and actions, `npm audit fix` and vitest 5 now, and the Riverpod 3 migration as its own change (an automated migration exists).

8. **Structure and naming: mostly clean, with a mislabelled layer, one oversized module and three verbs for one action (Low).** `PacketStoreService` lives in `Domain/` while doing Marten and Npgsql I/O; `Domain/Commands` are endpoint-to-service DTOs. `popup.ts` mixes DOM wiring, feed rendering, delete and undo, the copy menu, toasts and an icon atlas, with module-level `getElementById` calls that make it impossible to import under test. `packets_provider.dart` hosts two notifiers. The API says `Create`, the extension says send, the mobile app says push, and the title-ish field is `name`, `title` or `fileName` on the wire. The mobile app sends `?api-version=1` on every call and the extension sends none. Fix: "send" for user-facing verbs and `Create` for API names; split `popup.ts` into feed view, composer and toast modules behind a controller that receives its document and messaging so it can run under jsdom; move the store service to an application folder; pick one API-version convention.

9. **Client test gaps (Low).** Extension: `auth.ts` (URL building, prompt modes, state, nonce, audience and expiry checks), `api.ts` (the 401-refresh-retry-sign-out path, `readError`, the idle timeout), `live.ts` (port lifecycle, backoff), `background.ts` (delete scheduling and cancel, context-menu mapping), `cache.ts` and `popup.ts` have no tests. Mobile: 12 of 170 tests are widget tests; `PacketFeedPage`, `PacketList` (load-more trigger, error row, signed-out prompts), the send sheet, the tiles and `packet_helpers.dart` have none. No coverage is collected anywhere. Fix: vitest with `jsdom` and a stubbed `chrome` global for the popup modules, `fetch` stubs for the 401 matrix and problem parsing, fake timers for backoff and delete scheduling; Flutter widget tests with `ProviderScope` overrides reusing `test/fakes.dart`; coverage flags on all three Atom test targets.

10. **Deployment story is undefined (High for shipping, noted here for completeness).** `BuildWebApi` publishes to a folder; there is no container image, no infrastructure definition, no documented production configuration source, Marten runs DDL at startup, the extension version is a hard-coded "1.0.0" while .NET versions come from GitVersion, and there are no Web Store or Play publishing steps. Details and the fix are in [Developer Experience](developer-experience.md), finding 1.

11. **Nits.** `[PublicAPI]` on 54 declarations where `[UsedImplicitly]` or nothing says what is meant; npm `clean` and `package` scripts shell out to PowerShell; `pubspec.yaml` keeps about seventy lines of `flutter create` comments and `cupertino_icons`; `src/mobile_app/.flutter-plugins` is tracked although it says not to be, is stale and contains machine-specific paths; `ios/` carries sixty tracked scaffold files the docs call unconfigured; `avoid_print: false` disables a lint no code triggers; `Directory.Build.props` carries packaging properties no project packs; `IFlutterHelper` locates Flutter by string-matching `PATH` entries; 46 files start with a BOM and the worktree is 42 percent CRLF against an LF index (see [Developer Experience](developer-experience.md), finding 4).

## Decision: storage model for packets

Three reports converge on the same question. Packets are event-sourced (two or three events per stream, an inline snapshot), and nothing reads the history. The consequences: deletes never erase content ([Security](security.md), finding 1), the event table grows forever and bodies are stored twice ([Performance](performance.md), finding 6), creates and deletes cost extra round trips (finding 7 there), and every future feature (previews, pins, parcels) adds events and projection code.

| Option | Pros | Cons |
|---|---|---|
| **Keep event sourcing, archive and purge:** `ArchiveStream` on delete, partitioned archive, a purge job after N days, hard delete for account deletion | Smallest change; keeps the door open for per-user event replay | Content lingers until the purge; bodies still stored twice; rebuild and codegen complexity stays; every feature is an event plus projection work |
| **Plain Marten documents:** one `Packet` document with `Id`, `UserId`, `CreatedAt`, `DeletedAt` and the content union; `Store`, `Delete`, LINQ with the composite index | True deletes, half the writes, fewer round trips, simpler service and tests, features become fields; trash and restore is a `DeletedAt` field plus a purge | Rewrites `PacketStoreService`, the projection and their tests (about a day); loses an audit trail nothing uses |
| **Documents plus a per-user change log:** the above, plus a small `changes` table (user, sequence, packet id, change) written in the same transaction | Enables resumable SSE (`Last-Event-ID`) and `?since=` delta sync, which shrinks both client state machines (finding 3) | Slightly more code than plain documents |

Recommendation: plain documents, with the change log added when resumable sync is wanted (it is the natural companion of the device registry and push work). Record the decision as an ADR before parcels and previews add more events. If the team prefers to keep event sourcing, do the archive-and-purge option in Phase 0 regardless.
