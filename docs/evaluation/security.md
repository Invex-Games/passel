# Security

Scope: the API (authentication, authorization, input handling, live updates, database trust), the AppHost and local development setup, the Chrome extension, the mobile app, the Atom build and git hygiene. Method: an adversarial read of every component with evidence per finding, `npm audit` on the extension, a search of tracked files and git history for secrets, and a check of what the `.gitignore` rules actually cover. No server was run, so dev-tunnel behaviour and one Atom internal are marked unverified.

## Verdict

No critical or high findings. The authentication core is correct and fails closed: Google ID tokens are validated against Google's keys with explicit issuers and audiences, every handler re-checks the user id, every query is owner-scoped, foreign ids look like missing ids, the clients keep tokens out of persistent storage, and nothing secret is in the repository or its history. The material issues are about abuse and privacy rather than break-ins: anyone with a Google account can fill the database without limit, "delete" never erases content, there is no account deletion (a Play Store policy blocker), the dev tunnel publishes a Development-mode API to the internet, and event streams have no caps.

Score: 4 / 5 for exposure to attackers, 2 / 5 for abuse resistance and privacy obligations.

## Verified controls

These are right and worth protecting from regression.

- **Token validation** (`HostWebExtensions.cs`): `Authority` is `https://accounts.google.com` with HTTPS metadata required, signing keys come from Google's JWKS, signed tokens are required (so `alg: none` and key-confusion don't apply), `ValidIssuers` lists both Google issuer forms and `ValidAudiences` is the web client id plus the configured extras, so a token minted for any other Google app is rejected. Lifetime is checked with the default five-minute skew. If the client id is missing in production the audience list is empty and every token fails.
- **Identity and scoping:** `sub` becomes `ClaimTypes.NameIdentifier` and every handler returns 401 when it is absent. Reads filter by `UserId`, deletes check ownership and return 404 for missing and foreign ids alike, the SSE hub is keyed by user, and the notification listener re-verifies ownership before fanning out created packets. Email and `email_verified` are never used for authorization.
- **Development-only auth paths:** the cookie and Google OIDC login, the policy scheme and Scalar exist only under `IsDevelopment()`; production's default scheme is the bearer handler and unauthenticated requests get a plain 401.
- **Input limits:** URLs must be absolute `http` or `https` and at most 2,048 characters, names and titles 256, bodies non-blank and at most 64 K characters, `File` packets rejected, request bodies capped at 256 KB through endpoint metadata, JSON depth at the framework default of 64. Ids are checked for canonical encoding so aliases are impossible and malformed ids become 404s, never exceptions.
- **Live updates:** NOTIFY payloads carry ids only, never content, and are sent after commit; subscriber channels are bounded and close rather than drop; the heartbeat and client timeouts line up.
- **Errors and telemetry:** ProblemDetails and the exception handler give generic 500s outside Development; `LoggerMessage` calls log packet ids only; no request logging middleware; OpenTelemetry instrumentation captures no bodies.
- **Extension:** fresh `nonce` and `state` per sign-in, both checked along with `aud` and `exp`; the token lives in `chrome.storage.session`; message and port handlers reject other senders; no content scripts, no `externally_connectable`, minimal permissions, `host_permissions` derived from the API origin, the `key` pins the extension id so the OAuth redirect cannot drift. All rendering uses `textContent` and `createElement`; the only `innerHTML` is static SVG; only `http(s)` URLs become anchors, with `rel="noopener noreferrer"`. The cache is cleared on sign-out and account change.
- **Mobile:** token in memory only; a rejected token is never re-sent; redirects are not followed and HTML bodies are rejected; only `http(s)` links are tappable and they open externally; `allowBackup=false` with data-extraction rules excluding everything; only `INTERNET` requested; only the launcher activity exported; cleartext blocked by default; R8 plus Dart obfuscation on release; production builds refuse to build without release signing.
- **Secrets and git:** no client id, secret or key in any tracked file or in history (only placeholders); every local secret-bearing file is ignored (`*.Development.json`, both `.env` files, `*.keystore`, `local.properties`, `key.properties`); AppHost parameters go to user secrets and build secrets come from Azure Key Vault.

## Findings

Ordered by severity.

1. **"Delete" never erases content (Medium, privacy and compliance).** `PacketStoreService.Handle(DeletePacket)` appends `PacketDeleted`, and `PacketAggregate.ShouldDelete` removes only the inline snapshot. The `TextPacketCreated` body and `LinkPacketCreated` URL stay in `mt_events` forever; nothing calls `ArchiveStream` or deletes the stream, and archiving would retain the data anyway. There is no endpoint that deletes a user's data as a whole, no export and no retention job. Scenario: a user sends a password or a 2FA code to their phone and deletes it; it remains in every backup, in pgweb, and in any operator or attacker query. Someone who wants to leave can't. Google Play requires an account-deletion path for apps that sign users in, and GDPR erasure can't be satisfied without manual SQL. Options:
   - Keep event sourcing and hard-delete the stream in the same transaction (`QueueSqlCommand` against `mt_events` and `mt_streams`): minimal change, bends the event-store invariants.
   - Store packets as plain Marten documents and `Delete` them: true deletes, simpler, drops an audit trail nothing reads. Discussed as the storage-model decision in [Codebase Health](codebase-health.md).
   - A retention policy that expires packets after N days, regardless of the above: bounds storage and blast radius; a product decision.
   - Recommendation: plain documents plus retention, and in any case `DELETE /api/me` (everything where `UserId == sub`, then the user's open streams), a web page that performs the same deletion for the Play policy, and `GET /api/me/export` once the per-user query exists.

2. **No quotas or rate limiting (Medium, abuse and cost).** `Program.cs` and `HostWebExtensions.cs` register no rate limiter and no per-user caps beyond the 256 KB request limit; each create is an event, a snapshot and a NOTIFY. Token minting is open to the world by design: the extension's client id is public, the implicit-flow URL in `auth.ts` works from any browser, so anyone with a Google account can script the API. Scenario: a loop of 64 KB text packets from a throwaway account writes tens of gigabytes that finding 1 then can't reclaim; cheaper variants hammer the list endpoint or open thousands of streams. Fix: `AddRateLimiter` partitioned by `sub` (for example 30 creates a minute, 120 reads a minute, 429 on rejection) plus an application quota (maximum packets and bytes per user, checked with an indexed count before create). Proxy-level limits by IP are a weak third layer.

3. **The dev tunnel publishes the Development-mode API anonymously on a stable URL (Medium, developer exposure).** `AppHost.cs` adds the tunnel with `WithAnonymousAccess()`, the API runs as `Development` (Scalar, OpenAPI, the cookie and OIDC endpoints, `AutoCreate.All`, the developer exception page with stack traces), and the tunnel URL is compiled into every development APK and documented as stable. Scenario: anyone who sees a dev build, a screenshot or the dashboard has a persistent URL to the developer's workstation and, with a self-issued token, can read the OpenAPI document, fill the dev database and provoke stack traces. Whether the cookie login can complete through the tunnel depends on how the tunnel rewrites `Host` and is unverified; Google should reject the redirect URI, but nonce validation is off (finding 7) so don't lean on it. Fix: document `adb reverse tcp:7030 tcp:7030` as the default for USB-attached phones (and `10.0.2.2` for emulators); when a remote device is really needed, drop anonymous access and send the tunnel token from a dart-define; at minimum add `WithExplicitStart()` so the tunnel only runs when started from the dashboard, and consider `RequireHost("localhost")` on the dev endpoints.

4. **Event streams have no caps and outlive the token (Medium to Low, denial of service).** `PacketEventHub.Subscribe` appends channels per user without limit and `Publish` copies the list per event; `GetPacketEvents` ties a stream to `RequestAborted` and `ApplicationStopping` only, never to the token's `exp`; and after every LISTEN reconnect `PublishToAll(Resync)` makes every client refetch at once. Scenario: one account opens 20,000 streams, each holding a connection, a channel and an iterator; separately, a stolen token keeps delivering the victim's new packets for as long as the connection lives, hours past expiry. Fix: cap streams per user (five, completing the oldest so its client reconnects cleanly) and per instance (429 or 503 beyond it); `CancelAfter(exp - now + skew)` on the stream's token source so it ends when the identity would no longer authenticate, which the clients already handle by reconnecting with a fresh token; jitter the resync as described in [Performance](performance.md); and set `KestrelServerLimits.MaxConcurrentConnections` as a last line.

5. **Schema changes run under the API's role, and the NOTIFY channel trusts any writer (Low, trust boundary).** `AutoCreate.CreateOrUpdate` outside Development means the API's database role needs DDL rights and migrates at startup, racing across replicas. `PacketNotificationListener` parses any payload on the channel; created events are verified by loading the packet, but deleted events are forwarded unverified, so anything with database access can make clients hide a packet until restart, or trigger a load per notification. Database access is already game over, so the impact is low; the point is least privilege. Fix: `AutoCreate.None` in production, schema applied by the pipeline, a DML-only role for the API. Optionally store the user id as stream metadata so deleted notifications can be verified too.

6. **Open HTTP hygiene (Low).** CORS is `AllowAnyOrigin`, there is no HSTS, no HTTPS redirection, `AllowedHosts` is `*`, and there is no forwarded-headers handling. CORS creates no CSRF here because bearer tokens aren't ambient and `AllowAnyOrigin` forbids credentialed requests, and neither current client needs CORS at all (the extension's `host_permissions` bypass it, the app is not a browser). Fix: remove CORS until the web app needs it, then allow only its origin; add `UseHsts` outside Development or terminate TLS at the edge; set `AllowedHosts` to the API host; add `UseForwardedHeaders` if a proxy fronts the API.

7. **Development auth shortcuts (Low, dev only).** `ProtocolValidator.RequireNonce = false` disables replay protection on the OIDC response; the cookie scheme uses default secure-policy and same-site settings; and the AppHost launch profiles set `DOTNET_DASHBOARD_UNSECURED_ALLOW_ANONYMOUS`, so the Aspire dashboard on localhost shows the client secret and database password without its login token to any local process or DNS-rebinding page. Fix: delete the nonce line and fix the cause (usually the correlation cookie being dropped on the `/scalar` redirect; `SameSite=Lax` and `SecurePolicy=Always` on the correlation and nonce cookies), set the cookie to `Secure` and `Strict`, and remove the dashboard variable so Aspire prints a token.

8. **Release signing material handling (Low).** A real PKCS#12 keystore (`invex.keystore`) sits in the repository working tree; it is ignored and was never committed, but an ignore rule is not a secrets control: the folder gets zipped, synced, indexed and opened by IDEs. The build writes the Key Vault keystore to a fixed temp name and passes both passwords through environment variables to the Gradle daemon, deleting the file in a `finally` that a killed process skips. Fix: delete the working-tree copy (Key Vault holds it), write the temporary keystore under the OS temp directory with a random name and restrictive permissions, run release Gradle with `--no-daemon` so the signing environment doesn't linger, and confirm the process runner never logs environment variables (unverified in Atom's internals).

9. **Extension dev dependencies have known vulnerabilities (Low, supply chain).** `npm audit` reports four: `vitest` 3.2.7 with `tinypool` and `@vitest/mocker` (two critical, one moderate: prototype-pollution gadgets and mock-registration file read and code injection, all in the test runner) and `esbuild` 0.28.0 (low, dev-server file read on Windows; the project never uses `serve`). Nothing ships to users: the bundle has zero runtime dependencies. Fix: `vitest@^5` and `esbuild@^0.28.1`, rerun the tests.

10. **Informational.**
   - Public ids are reversible Sqids over UUIDv7, so a holder of an id can read its creation timestamp; with 74 random bits and owner scoping everywhere, enumeration is infeasible and the leak is only to the owner. Revisit if ids become shareable links.
   - A stolen ID token is usable for up to about 65 minutes with no revocation; inherent to ID-tokens-as-bearer and mitigated by TLS and the clients' storage choices. First-party sessions ([Features](features.md), item 7) add revocation.
   - Response compression over HTTPS is not a BREACH risk today because responses contain only the caller's own data and no reflected secret; re-evaluate if a share token ever appears in a response.
   - `/health` is unauthenticated and includes the database check but returns only the aggregate status; restrict it to the internal network if the platform allows.
   - "Send Current Page" sends `tab.title` and `tab.url` untruncated, so pages with titles over 256 characters or URLs over 2,048 fail; truncate the name client-side.
   - The extension's SSE parser buffer is unbounded; only the pinned API can abuse it, but cap it at a megabyte and reconnect.
   - The undo window lives in the service worker's memory, so a worker termination inside the four seconds loses the delete. Functional only.
   - The Flutter SDK is cloned by tag rather than commit, and the build runs `git clean` and `checkout --force` on a developer's own SDK; pin a commit for reproducible builds.
   - `Aspire.AppHost.Sdk` 13.3.1 and `Aspire.Hosting.*` 13.6.2 are out of step; align them.
   - The uncommitted `.vscode/launch.json` change adds a personal device serial; keep it out of the commit.
