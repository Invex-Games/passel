Request pipeline

Program.cs adds the service defaults and the web defaults (Extensions/HostWebExtensions.cs). Those cover JSON options, ProblemDetails, compression, authentication, rate limiting and API versioning, plus the edge: a Kestrel connection limit, forwarded headers when a proxy is declared, host filtering, and HSTS outside Development. CORS allows the web app's origins only (Cors:AllowedOrigins, see Configuration), with no credentials, and answers preflights ahead of authentication (Extensions/CorsExtensions.cs). It then maps the packet, device and parcel endpoints (Endpoints/EndpointMapper.cs). In development it also maps OpenAPI, Scalar and the browser login endpoints (Extensions/HostDevExtensions.cs), in one route group that only answers to the localhost host (RequireHost), so they are not served through the dev tunnel; the packet, device and parcel endpoints answer to any host.

Every packet endpoint lives under /api/packets, every device endpoint under /api/devices and every parcel (uploaded file) endpoint under /api/parcels; all of them require authentication and are API version 1. The parcel group also runs ParcelResponseHeadersFilter on every request, which adds the sandboxing and caching headers to whatever the endpoint answers; see Parcels. The user id is the Google sub claim. See HTTP API for the endpoints themselves.

A body that cannot be read (malformed JSON, a missing or unknown discriminator, an unknown enum name, a missing required property) is a 400 in every environment: the web defaults turn off RouteHandlerOptions.ThrowOnBadRequest, which Development otherwise sets, so the request never reaches the exception handler as a 500, and the status code pages write the problem. A union body without its $type needs one more step, because System.Text.Json cannot create the union's abstract base and reports that with a NotSupportedException, which body binding does not count as a bad request. A type info modifier on the HTTP JSON options (HostWebExtensions.RequireTypeDiscriminator) gives every such base a factory that throws a JsonException instead.

Abuse controls

Each endpoint opts into one of six rate-limiting policies (Extensions/RateLimitingExtensions.cs): packet creates, reads (the packet list and delete endpoints, and the device list), event-stream connections, device writes (every other device endpoint), parcel uploads (uploads and discards) and parcel reads (downloads and thumbnails, generous because a feed page can show fifty thumbnails). The limiter runs after authentication so requests are counted per user; requests that fail authentication are counted per remote address instead. Rejections are 429 problems with Retry-After. The limits come from the RateLimits configuration section; see Configuration.

Before a create, PacketQuotaService reads the caller's usage with one aggregate over the packet table (count(*) and the summed pg_column_size of the documents, through the leading member of the index on UserId and Id), and PacketQuota.Exceeded compares it with the Quotas configuration. A user at the packet limit gets 429, a packet that would pass the byte limit gets 413, and both messages say to delete packets. Two creates that race can both pass the check, so the quotas are approximate by a packet. The device cap works the same way (DeviceQuota.Exceeded against a count of the user's devices, 429 when reached), but only for an installation that registers for the first time; see Device registry. Nothing ties the count to the insert, so every registration of a new installation in a burst can pass it: a user one below the cap can get past it by as many registrations as the device-writes limit admits at once, RateLimits:DeviceWritesPerMinute less one, and more behind several API instances, since each instance counts the limit in memory. The rate limit bounds the excess; enforcing the cap exactly would mean serialising a user's registrations in the database, which a bound on rows of a few dozen does not justify.

Uploaded files have a quota of their own, separate from the packet byte quota, which counts packet documents only (a File packet counts its name and a fixed 64 bytes there). ParcelQuotaService reads it with one aggregate over the parcel table: the number of files uploaded but not sent (still uploading, or uploaded and in no packet) and the summed Size of every file not deleted, through the index on UserId. ParcelQuota.Exceeded refuses an upload with 429 at Quotas:MaxPendingParcelsPerUser unsent files and with 413 when it would pass Quotas:MaxParcelBytesPerUser; ParcelQuota.TooLarge gives the 413 for one file over Parcels:MaxParcelBytes. An upload is checked twice: before its body is read, against the size it declares (or the largest file allowed, for a body without a length), which it then reserves by recording the parcel at once; and again with its exact size once it is stored. Two uploads that race the first check can both pass it, so this quota is approximate too, by the uploads that arrive in the same moment.

Storage: Marten documents

Packets are stored with Marten on PostgreSQL, as plain documents (ADR 0001).

  • Each packet is one Packet document (Domain/Packet.cs) in the mt_doc_packet table: Id, UserId, CreatedAt and the Content union (Link, Text or File, stored with a $type discriminator). The id is a version 7 Guid, so id order is creation order; the feed and its cursor rely on that. A Link also carries its Preview once one has been fetched; see Link previews.
  • PacketStoreService handles creating and deleting packets, and attaching a link's preview: one upsert to create, one delete to remove, one update for the preview. Deleting checks ownership first. A missing packet and someone else's packet both return 404, so ids can't be probed. A delete removes the document, and nothing else keeps the content. A File packet is the exception in both directions: creating one also attaches its parcel, and deleting one also marks its parcel deleted, each in the same commit; see Parcels.
  • The documents carry one composite computed index on UserId and Id, which serves the feed query. See The feed index.
  • In Development, Marten applies the schema at startup (ApplyAllDatabaseChangesOnStartup), so the table exists before the first request; the quota check reads it with plain SQL, which Marten's on-first-use creation would not cover. Everywhere else the deployment applies it; see Schema in production.
  • The data source comes from Aspire.Azure.Npgsql (Extensions/HostDatabaseExtensions.cs): a connection string with a password is used as it is, and one without signs in with a Microsoft Entra token for the managed identity, as the Azure deployment does.

The bytes of uploaded files are not in the database: each upload is one Parcel document (Domain/Parcel.cs, table mt_doc_parcel) whose bytes are in the parcel store (Azure Blob Storage, or a directory on the server's disk when self-hosted), and a File packet refers to it by id. See Parcels.

A database from before the move still has the event-sourcing tables (mt_doc_packetaggregate, mt_events, mt_streams); nothing reads them, and they can be dropped. Marten does not migrate the old packets into the new table.

Schema in production

Outside Development the API never changes the schema (ADR 0003):

  • The store uses AutoCreate.None, so nothing is created or altered at runtime, and the API's database role needs no more than DML.
  • At startup, before anything else starts, it checks that the database has every schema, table, column and function its configuration declares (Services/DatabaseSchemaCheck.cs) and refuses to start otherwise, so a revision whose migration didn't run never becomes ready. What it finds beyond that, such as a column or an index a newer release's migration added or a Marten function it changed, is logged and accepted: the previous revision keeps serving, and restarting, on that schema until the new one is ready, and for good if the deployment fails after its migration. Marten's own AssertDatabaseMatchesConfigurationOnStartup refuses any difference, so it isn't used; db-assert still runs that strict comparison.
  • The deployment's migration job applies the schema before each new revision starts, by running the API's image with the db-migrate command.

db-migrate (Extensions/MigrateDatabaseCommand.cs, Services/DatabaseMigrator.cs) logs in as a role that may change the schema, and then:

  1. Applies the configured schema with AutoCreate.CreateOrUpdate, with every table marked add-only (Weasel's AddOnlyMigrations). It creates what is missing, alters what changed and replaces Marten's functions, but never drops a table, or a column, index or foreign key that the configuration no longer declares: it logs each one it leaves in place. Plain CreateOrUpdate would drop them, and with them the data in a column, so rolling back to an older release would delete what a newer one added.
  2. Creates the role passel_app if it doesn't exist (no login), and grants it select, insert, update and delete on the tables in the store's schema, use of its sequences and execution of its functions, now and, through default privileges, on what the migration creates later.
  3. If Database:ApiRole is set, makes that role a member of passel_app. If Database:ApiRoleObjectId is set too, it first creates the role as a Microsoft Entra principal of that managed identity (a login role carrying the pgaadauth security label), so the API can sign in with tokens.

Every step is idempotent, so the job runs on every deployment. The API's role can then read and write packets, listen and notify, and run the quota query, but not create, alter or drop anything; the integration tests check both sides.

Program.cs runs JasperFx's command line when the first argument names a command, and the API otherwise. Besides db-migrate, db-assert checks a database against the configuration, db-patch <file> writes the statements a migration would run without running them, and help lists the rest. Both use Marten's plain comparison, so db-patch also lists the drops db-migrate leaves out, which makes it the way to write one by hand. For example, against the database in appsettings.Development.json:

dotnet run --project src/webapi/Invex.Passel.WebApi -- db-patch patch.sql

There is no code generation step. Marten 9 removed runtime code generation, so there is nothing for codegen write to produce and nothing to regenerate when a document type is added. A unit test (DatabaseSetupTests) fails if a package ever registers code that would need generating ahead of time; that is when to add codegen write to the build, with a check that its committed output is current.

The feed index

GET /api/packets runs where UserId = ? and Id < ? order by Id desc limit 51. With the index declared as .Index([p => p.UserId, p => p.Id]), Marten emits the identity member as the id column rather than a JSON expression, so the query becomes a backward range scan of at most 51 index entries however many packets the user has:

CREATE INDEX mt_doc_packet_idx_user_id_id ON public.mt_doc_packet USING btree ((data ->> 'UserId'), (id));

Program.cs sets the name; the one Marten derives runs the members together as user_idid. The single-column index on UserId that the API used to declare is gone, because the leading member of this one serves the same lookups, including the quota aggregate.

Measured on PostgreSQL 18.3 with 15,021 packets seeded through the API (one user with 5,001, fifty users with 200 each), EXPLAIN (ANALYZE, BUFFERS) of the exact statements Marten emits, warm, after ANALYZE. The measurements were taken on the snapshot table of the event-sourced model; the document table has the same columns and the same index, so the plans are the same:

Query Index on UserId only Index on UserId, Id
First page, user with 200 packets Index Scan Backward on the primary key, filtering on the JSON expression: 7,322 rows discarded, 7,399 buffers, 0.89 ms Index Scan Backward on the composite index: 53 buffers, 0.03 ms
Cursor page, same user The same walk from the cursor: 2,551 rows discarded, 2,608 buffers, 0.35 ms Index Cond on both members: 50 buffers, 0.03 ms
First and cursor page, user with 5,001 packets Primary-key walk: 53 buffers, 0.02 to 0.03 ms Unchanged. A third of the table is this user's, so the walk finds 51 rows at once and the planner keeps it
Quota aggregate, user with 200 packets Bitmap scan on the index: 172 buffers, 0.07 ms Bitmap scan on the composite index: 173 buffers, 0.07 ms

The primary-key walk reads every newer packet of every other user until it has 51 of the caller's, so it gets worse with every user added; the composite index reads 51 entries whatever the table holds. Two things to know: the planner only prefers the index once it has statistics on the expression, so run ANALYZE after creating it on a database that already has data (autovacuum gets there eventually), and the index is larger than the single-column one was (744 kB against 120 kB for these rows), because PostgreSQL deduplicated the old one's fifty-one distinct keys.

Public ids

Packet, device and parcel ids are never exposed as raw Guids. IdEncodingService encodes the Guid's two 64-bit halves with Sqids (minimum length 10). The alphabet comes from Encoding:Alphabet. Changing it invalidates every id that clients have stored.

Live updates

GET /api/packets/events streams server-sent events to signed-in clients:

  1. After a create, a delete or a preview update commits, PacketStoreService sends a PostgreSQL NOTIFY on the passel_packet_events channel. The payload carries the user id, packet id and the change (Created, Deleted or Updated).
  2. Each API instance runs PacketNotificationListener, a hosted service that LISTENs on that channel on its own connection. It reconnects after 5 seconds if the connection fails, and sends a keep-alive query when the connection is idle. Npgsql raises one notification per wait on the connection, so the connection loop only queues what it parses, and a dispatch loop takes everything queued at once as a batch: it loads the created and updated packets of users with a stream open on the instance with one query, publishes per user in arrival order (packet-created or packet-updated, each carrying the packet as it is now), and publishes deletes without a load. If the query fails, each affected user gets a resync instead.
  3. The listener publishes to PacketEventHub, an in-memory hub on that instance. The hub fans events out to each user's open streams through bounded channels of 64 events.

Because every instance listens, events reach clients connected to any instance. The stream doesn't support resuming. Instead, clients reconnect, receive resync, and fetch GET /api/packets again. The server also sends resync when it may have missed events: after the listener reconnects, every open stream on the instance gets one, spread at random over three seconds so that the re-fetches don't all reach a database that may just have recovered at the same moment. If a stream's buffer fills, the server closes the stream rather than drop events.

A stream sends a ping after 20 seconds without events. The wait is a delay that completes rather than a timeout that throws, because every idle stream times out every 20 seconds. The first event of a stream carries an SSE retry value drawn per stream between 2 and 6 seconds, so clients that honour it (a browser EventSource does; the extension and the mobile app use their own jittered backoff) reconnect spread out after a restart. Event-stream requests are left out of request tracing in ServiceDefaults, next to the health endpoints, because a stream's request lasts up to a day and its trace would hold an activity open for all of it.

Streams are capped by the EventStreams configuration. The hub keeps at most five per user on an instance: subscribing a sixth removes the oldest from the hub and completes its channel, so that client's stream ends cleanly and it reconnects. Beyond the per-instance total, Subscribe returns null and the endpoint answers 503 with Retry-After. The subscription is registered for disposal with the response, so the hub releases it when the stream ends however it ends.

A stream never outlives the token that opened it: the endpoint reads the exp claim and cancels the stream at exp plus the bearer handler's clock skew (PacketEndpoints.StreamLifetime), with a ceiling of a day for principals without an expiry. The clients already reconnect with a fresh token.

Link previews

When a link packet is created, its page is fetched in the background and what the page says about itself is stored on the link (LinkPreview on PacketContent.Link: title, description, image URL and when they were read). The fetch never runs inside the request: PacketStoreService queues it on LinkPreviewQueue, a bounded in-memory channel, once the create has committed, and LinkPreviewWorker, a hosted service, runs the queued fetches a few at a time. A fetch still queued when the instance stops is lost, and the link then keeps no preview, which is the same outcome as a page that gave none.

The API is fetching URLs that users chose, so LinkPreviewFetcher is held to rules that no configuration loosens:

  • Only absolute http and https URLs without credentials are requested, on the URL the user sent and on every redirect. Nothing else is ever fetched: not the image a page names, not the links on it.
  • The fetcher resolves each host itself and checks every address it gets with LinkPreviewAddressPolicy, which allows public unicast addresses only: no loopback, private (10/8, 172.16/12, 192.168/16), carrier-grade NAT (100.64/10), link-local (169.254/16, where the cloud metadata services live), multicast, reserved or documentation ranges, in IPv4 or IPv6. An IPv6 address that stands for an IPv4 one (IPv4-mapped, NAT64) is judged by that address; the deprecated IPv4-compatible and 6to4 forms are refused outright. If any address of a host is refused, the whole fetch is.
  • The connection is made to one of the checked addresses, through the handler's connect callback, never to a fresh resolution of the name, so a name whose answer changes between the check and the connection (DNS rebinding) gets the checked address all the same. TLS still validates the certificate against the host name. No proxy is used, and no cookies.
  • Redirects are followed by hand, at most three, each hop checked like the first URL.
  • Only text/html and application/xhtml+xml responses are read, at most 512 KB of them and no further than the end of the <head>, within one five-second budget for the whole fetch, redirects included. No Accept-Encoding is sent, so the cap counts the bytes the page sends.

LinkPreviewExtractor reads the head, with comments, scripts and styles taken out, for the Open Graph tags first, the Twitter card tags next, and the plain <title> and <meta name="description"> last. Entities are decoded, whitespace collapsed, the title cut to 256 characters and the description to 512, and a relative image URL made absolute against the page; an image that is not an http or https URL is dropped. A page with no title, description or image gives no preview.

A failure that may pass (a timeout, a connection or DNS failure, a 429 or 5xx answer) is retried: three attempts in all, five seconds before the second and ten before the third. A refusal, a 4xx answer, a page that is not HTML or one redirect too many is final. Either way, a failed fetch shows up only as the link keeping preview: null, plus one Debug log line naming the packet and the reason; nothing is stored or announced about it. The reason can name the linked host, which is why it is not logged at Information. For the same reason the fetches are left out of the traces, and outgoing HTTP metrics carry no host name; see Logs and telemetry.

When something was found, the worker attaches it through PacketStoreService with a Marten update rather than a store: a store is an upsert and would bring back a link deleted between the fetch and the save, whereas Marten refuses to update a document that is gone, and the preview is dropped with it. The commit is followed by a NOTIFY with the change Updated, which the listener loads like a create and the streams send as packet-updated, carrying the link in the PacketResponse shape with its preview set. The limits, the retry policy and the concurrency come from the LinkPreviews configuration section; the address rules do not. See Configuration.

The integration tests fetch from a Kestrel server of their own on the loopback (TestPageServer), reached by the name pages.test, which the test factory's stand-in resolver points at the loopback while it resolves every other name to a private address. So the suite never reaches the internet, and the address rules stay in force for everything but that one name.

Device registry

The device endpoints (Endpoints/DeviceEndpoints/) keep a list of each user's devices: what the push sender (roadmap 2.B1) will deliver to, what first-party sessions (1.B1) will belong to, and what "send to a device" will target later. Nothing sends pushes yet, and no client registers yet (2.D3 and 2.E2).

Each device is one Device document (Domain/Device.cs) in the mt_doc_device table: Id, UserId, the client's InstallationId, Name, Platform (Android, Extension or Web), CreatedAt, LastSeenAt, and the push token (Push, a union of Fcm and WebPush stamped with UpdatedAt) with its PushKey. DeviceStoreService writes them, and DeviceEndpoints.DeviceResponse.From is the one mapping to the wire.

  • The id is the API's. A version 7 Guid, encoded like a packet id. It is what anything else refers to a device by, so a session can be revoked with its device (1.B1). It is never reused: a removed installation that registers again gets a new one.
  • Registering is idempotent. The client generates its installation id once and sends it every time; a unique index on UserId and InstallationId (mt_doc_device_uidx_user_id_installation_id) makes a second registration of the same installation find the first device, even when several arrive at once: the losers of the insert get a unique violation, read again, and answer with the winner's device without writing it. In the same way, registrations of a known installation that lose the race to move LastSeenAt find it moved by the winner and answer with that, so any number of racing registrations settle in two attempts. A known installation keeps its name, so a rename made in settings survives the next start, and only LastSeenAt moves. The same installation under another account is another account's device. The index's leading member also serves the device list and the count for the cap.
  • A push token belongs to one device. PushKey is the SHA-256 (lower-case hex) of the kind and the FCM token or Web Push endpoint, and a unique index covers it (mt_doc_device_uidx_push_key); devices without a token leave it null, which the index allows any number of times. Hashing keeps the index entries small however long a token is, and a unique-violation message names a hash rather than the token. Setting a token first takes it off any other device that holds it, of any user, in the same commit: a token identifies an installation or a browser profile, not an account, so after a sign-out and a sign-in as someone else it arrives from the second account's device, and the first account must stop pushing to it. The move is logged at Information with the two device ids.
  • A token's kind follows the platform. Fcm on Android, WebPush (endpoint, p256dh, auth) in the extension and the web app; the store refuses the other kind. A Web Push endpoint must be https, on a host name and the default port, because the sender will make requests to it. That does not make it safe to call: 2.B1 has to check the addresses the name resolves to, as the link preview fetcher does.
  • Tokens stay in. The wire shape has pushUpdatedAt and nothing else of the token. Nothing logs a token, the token records override ToString so that printing a device or a request never shows one, and validation messages never repeat it. Marten logs a failed command with the document as binary, so a race leaves no token in the logs either.
  • Changes never undo each other. Every change is a Marten update of the whole document, with optimistic concurrency on the device type. An update of a device that is gone (NonExistentDocumentException), that has changed since it was read (ConcurrencyException), or a write of a unique key another request has just written, is a lost race: the store drops its changes, reads again and decides afresh, at most three times. A rename that loses to a removal answers 404; a registration that loses to one makes a new device. A write that loses all three times (several renames or push token changes of one device at the same moment) throws DeviceWriteConflictException, which DeviceWriteConflictHandler answers with a 409 problem saying to send the request again, and logs at Warning.
  • Lost races are logged by Marten. Marten logs a failed command at Error before the store sees the exception, so each lost insert (racing first registrations of one installation) and each lost push key (two devices given one token at the same moment) leaves a Marten.IDocumentStore error with PostgreSQL's 23505 unique violation, although the store handles it. Such races need clients sending at the same moment and are rare; an error naming mt_doc_device_uidx_user_id_installation_id or mt_doc_device_uidx_push_key with no failed request next to it is one of them.

What 2.B1 needs from the document is the platform, the token and its UpdatedAt (FCM advises dropping tokens that have not been refreshed for a long time), and LastSeenAt. When a push service says a token is gone (FCM's UNREGISTERED, a Web Push 404 or 410), the sender should clear it the way ClearDevicePush does.

Parcels

A parcel is an uploaded file (Endpoints/ParcelEndpoints/): one Parcel document (Domain/Parcel.cs) in mt_doc_parcel, with its bytes in the parcel store: Azure Blob Storage, or a directory on a local disk for a self-hosted deployment (ADR 0004). Sending a file is two requests, an upload to POST /api/parcels and a File packet that names the parcel; see Parcels in the HTTP reference. No client uploads or shows files yet (roadmap 2.C2, 2.D2 and 2.E2).

From To When
(nothing) Uploading An upload starts, before its body is read
Uploading Uploaded Its bytes and thumbnail are stored
Uploading Deleted The upload fails, or is still unfinished after Parcels:UploadingGrace (15 minutes)
Uploaded, in no packet Deleted The user discards it, or Parcels:UnattachedLifetime (an hour) passes
Uploaded, in a packet Deleted Its packet is deleted, or the orphan scan finds the packet gone
Deleted erased The sweep deletes the thumbnail, then the original, then the document

Whether a parcel has been sent is not a status: it is AttachedPacketId. Three services change parcels: ParcelStoreService records, completes, fails and discards uploads, PacketStoreService attaches a parcel to its File packet and marks it deleted with the packet, and ParcelSweep expires and erases. Every change is a Marten update with optimistic concurrency on the parcel type.

  • The document comes before the bytes. An upload records an Uploading parcel first, reserving its declared size against the quota, so uploads that follow at once see it. Its body is read as it arrives with MultipartReader, never bound as a form, through CountingHashStream, which counts it, hashes it with SHA-256 and stops at Parcels:MaxParcelBytes, into a temporary file that deletes itself when closed. Then it is inspected, the original and the thumbnail are put, the quota is checked again with the exact size, and the parcel becomes Uploaded with its size, type, dimensions and hash. Anything that goes wrong after the parcel is recorded marks it Deleted, so the sweep erases whatever of it was stored; if even that fails, it stays Uploading until the grace period expires it. At most Parcels:MaxConcurrentUploads (4) uploads run at once on an instance (ParcelUploadGate); the next waits five seconds and then gets 503 with Retry-After. The temporary files therefore take at most that many times the file limit of the container's disk.
  • Blobs are named after the parcel. ParcelKeys derives the names from the id alone, {id:N} for the original and {id:N}.thumb for the thumbnail, so nothing stored can drift from the document, and blob URIs, which the Azure SDK records, name no user and no file. A put never overwrites (If-None-Match: * in Azure, a rename that refuses an existing file on disk). There is no deduplication across users, which would tell one user that another holds the same file.
  • The type comes from the bytes. ParcelSniffer reads the first 1,024 bytes for JPEG, PNG, GIF, WebP and PDF signatures; everything else is application/octet-stream, HTML, SVG, HEIC and AVIF included, and the type the client declared is never stored. Only an image that decoded, or a PDF, is served inline; anything else is an attachment, and every parcel response carries Content-Security-Policy: sandbox; default-src 'none', nosniff and no-referrer, so a file is never run as a page on the API's origin. The filter also turns response compression off for the group, which would drop the length, break ranges and weaken the strong entity tag.
  • Images are checked before they are decoded. ParcelInspector opens the file with SkiaSharp's SKCodec, which reads the header and allocates no pixels, and goes on only when the format is JPEG, PNG, GIF or WebP and matches the sniffed type (Skia also decodes BMP, WBMP and ICO, which are refused here). An image over Parcels:MaxImagePixels (40 million) or Parcels:MaxImageDimension (16,384 on a side) is not decoded at all, so a small PNG that claims to be 100,000 pixels square costs nothing. JPEG and WebP decode at a reduced scale close to the thumbnail size; PNG and GIF can only decode at full size, which at the pixel cap is 160 MB of native memory, so decodes run one at a time on an instance. An upload waits at most Parcels:DecodeSlotTimeout (five seconds) for its turn and is otherwise stored as a plain file of its sniffed type, with no thumbnail and the failure decoder busy logged, so one slow decode delays the uploads behind it by that much at most rather than holding them all. Only a complete decode counts: a truncated image is a plain file. The first frame is resized (Mitchell), turned upright by its EXIF orientation, and encoded as lossy WebP with no colour space, so the thumbnail carries no ICC profile and Skia writes no EXIF or XMP. A file that fails any step is stored as a plain file without a thumbnail, and the step is logged at Information with the parcel id. The wait for the slot is bounded but the decode itself is not: a Skia decode is a native call that can't be cancelled, so the pixel cap is what bounds its time and memory. A progressive JPEG is the slow case left: Skia gives no cheap way to tell one from the header, and it buffers and entropy-decodes every coefficient of the image however small the scale asked for, so one near the pixel cap is far slower than a baseline JPEG of the same size; the cap and the bounded wait are the whole defence.
  • The original is kept byte for byte, EXIF and GPS included, so the download is lossless and its SHA-256 is a strong entity tag. Only the thumbnail is stripped. The HTTP reference says so to clients.
  • A parcel is sent once. Creating a File packet loads the parcel, stores the packet and updates the parcel's AttachedPacketId in one commit. Two sends of one parcel both update the same parcel document, so the version check alone decides between them: the loser's commit fails, writes nothing, and it answers 409. The unique index on AttachedPacketId (mt_doc_parcel_uidx_attached_packet_id) guarantees the other direction, that no packet id is on two parcels; unsent parcels leave it null, which the index allows any number of times.
  • Deleting a packet deletes its file. PacketStoreService.Handle(DeletePacket) marks a File packet's parcel Deleted in the same commit as the packet's delete, and after the commit wakes the sweep. The request does no blob I/O. If marking the parcel loses a race (the sweep expiring it, say), the packet is deleted alone, and the orphan scan releases the parcel later.
  • The sweep erases. ParcelSweepWorker, a hosted service, runs ParcelSweep when it is woken (a packet delete, a discard and a failed upload all wake it) and otherwise every Parcels:SweepInterval (five minutes). A run expires parcels left unsent past their lifetime and uploads stuck past their grace, each with a version check, so a send that commits first keeps its parcel; then erases Deleted parcels in batches, the thumbnail first, the original next and the document last, so a run cut short only repeats a delete that is already idempotent. A parcel whose bytes can't be deleted (storage down) stays Deleted for the next run. So a deleted file's bytes are gone within seconds, and at worst after one sweep interval while storage is reachable. The sweep sends no packet events. It logs counts at Information and parcel ids at Warning, never a user id or a file name.
  • The orphan scan catches the rest. Every Parcels:OrphanScanInterval (a day, the first a full interval after the instance starts), the sweep also marks Deleted any sent parcel whose packet is gone, and deletes blobs older than Parcels:OrphanBlobMinimumAge (two hours) that no parcel document names. An upload always records its document before its first blob, so a blob that old without one is left over rather than in flight; a blob name that doesn't parse as a parcel's is logged and left alone. This is also what removes blobs left behind when Development's AutoCreate.All recreates the parcel table. The scan lists uncommitted blobs too, and the filesystem store the temps of uploads in progress, so what an upload staged before it was cut off (an instance stopping mid-upload) is found like any other name. Every step is idempotent or version-checked, so instances sweeping at the same time do no harm.
  • Deletes are true deletes (ADR 0001). The Azure storage account has blob soft delete and versioning off, so a deleted blob is not kept; container soft delete (seven days) protects against losing the container, not a file. Turning blob soft delete on would keep every deleted file for its retention period. On disk a deleted file is unlinked; only the server's backups keep it, for as long as they are kept.
  • Storage is not a health check. /health is the readiness probe of the only replica, and a storage outage must not take texts and links down, so the blob client's health check is off. Storage failures surface on the parcel endpoints instead: ParcelStoreUnavailableHandler answers an Azure RequestFailedException, the filesystem store's ParcelStoreFailedException (a full disk, a directory the API cannot write) or the stand-in store's exception with a 503 problem and Retry-After: 30, and logs a Warning with the status and error code, or the operation, the blob name and the type of the disk's error, never its message, which names the path. Other I/O errors are not storage failures: a client that stops sending its upload is an IOException too. A host with no store configured (the db-migrate job, which runs Program.cs without storage settings) registers UnavailableParcelStore, so it still builds and every file request answers 503; outside Development it logs a Warning at startup.
  • Lost races are logged by Marten. As with devices, Marten logs a failed commit at Error before the service sees the exception, so two sends of one file at the same moment, and a send or a delete that collides with the sweep, each leave a Marten.IDocumentStore error with a concurrency failure on a parcel although the race was handled. An error like that with no failed request beside it is one of these.

Parcels:Store picks the store when the host is built (Extensions/HostParcelExtensions.cs). Auto, the default, picks Azure when the passel-blobs connection string is set and UnavailableParcelStore otherwise, which is what the AppHost, the Azure deployment and the integration tests' shared host rely on; AzureBlob picks Azure and fails the options' validation at startup without the connection string; FileSystem picks FileSystemParcelStore, whose root, Parcels:FileSystemRoot, must be an absolute path. Neither store touches storage until it is used, so the db-migrate job builds the same host without a volume or a storage account.

AzureBlobParcelStore uses the BlobServiceClient that Aspire.Azure.Storage.Blobs registers for passel-blobs (a connection string locally, the account's blob endpoint and the managed identity in Azure), and the container Parcels:ContainerName, which it creates if it is missing before its first write. A read is pinned to the blob's ETag and gives a seekable stream of known length, which is what lets Results.Stream answer ranges. appsettings.json keeps Azure.Core at Warning, because the client forwards the SDK's event log, which logs every request, blob URI included, at Information. A delete also erases an upload that never finished: a file over 4 MB goes up as staged blocks that become a blob only when committed, so when there is no blob under the name, the delete looks for uncommitted blocks and, if there are any, commits an empty block list over them (only while there is still no blob) and deletes the empty blob, which discards them; otherwise Azure would keep them for about a week. A parcel is erased only once it is Deleted, so an upload still running under that name has had its parcel failed or expired, and its own commit then fails. Azurite still lets a later commit of the discarded blocks succeed, so the tests check that the delete leaves no blob and no block list under the name, not that a later commit of those blocks fails.

FileSystemParcelStore keeps each blob as the file {root}/{name}, flat, and writes an upload to {root}/.uploading/{name}.{random}.tmp first: it copies the bytes in, flushes them to disk, renames the temp into place without overwriting (an existing file fails the put as Azure's condition does), and then flushes the root directory itself on Linux (Services/PosixDirectory.cs, which calls libc's open and fsync), because the parcel is recorded as uploaded the moment the put returns and a rename that is not flushed can be lost in a power cut. A blob is therefore whole or absent. Only the two names ParcelKeys makes are accepted, so no name can lead out of the root. Reads open the file directly, sharing it for deletion, so the sweep can erase a file while it downloads. A delete removes the temps of that name, then the file: an upload still writing finds its temp gone when it renames and fails as discarded (Upload discarded, 503), as an Azure upload does whose blocks were discarded, and the temps of the original and the thumbnail are told apart although they share a prefix. The list gives the files in the root and the names of the temps, each as old as its last write, so a running upload keeps looking young to the orphan scan, and a crashed one is erased with its parcel or by the scan. Its own disk failures become ParcelStoreFailedException; a failure of the stream it copies from is thrown as it is. Files are created 0600 and the temp directory 0700 on Linux, for the API's own user. The root must be on a local disk: on a network share the rename that refuses to overwrite and the flushes are weaker than the store relies on.

Thumbnails use SkiaSharp 3.119.4 (MIT), with SkiaSharp.NativeAssets.Linux.NoDependencies for Linux: the aspnet:10.0 image the API runs on has no fontconfig, and that build of libSkiaSharp.so needs only libc, libm, libdl and libpthread (no text is drawn). The Windows and macOS native assets come with SkiaSharp itself, for local development. ImageSharp was ruled out: from 3.2.0 its Release builds require a Six Labors licence key, and 3.1.12 fails restore on known advisories.

Authentication

Clients send a Google ID token as a bearer token. The API validates it against Google with these accepted audiences:

  • Authentication:Google:ClientId
  • Authentication:Google:AdditionalAudiences

In development a policy scheme picks how each request is authenticated:

  • A request whose Authorization header is Dev <user-id> uses the Dev scheme (Authentication/DevAuthenticationHandler.cs): it signs the request in as that user, with the id as both sub and display name, and no Google involved. The scheme only exists in Development; see Run without Google.
  • A request with any other Authorization header uses bearer tokens.
  • Any other request uses a cookie, issued by Google OpenID Connect login, when Authentication:Google:ClientId and ClientSecret are both set. Without them there is no cookie login, so such a request gets a plain 401 from the Dev scheme.

In Development the Google settings are optional: the bearer handler is still registered, but with no client id its audience list is empty and every Google token is rejected. The OpenAPI document declares the Dev scheme so Scalar can send its header, and the Scalar banner says when Google login isn't configured.

That cookie login is what lets Scalar call authenticated endpoints. The login cookie is Secure and SameSite=Strict. The OpenID Connect correlation and nonce cookies are Secure and SameSite=Lax, which works because Google returns the code in a top-level GET (response_mode=query), and the nonce in the ID token is validated. Production only accepts bearer tokens, and unauthenticated requests get a plain 401.

See Google OAuth Clients for which client is which.

Integration tests

Invex.Passel.WebApi.IntegrationTests runs the API as Program.cs builds it, in the Development environment, against a real PostgreSQL and a real blob store (Azurite). The suite needs Docker running and nothing else:

dotnet test --project src/webapi/Invex.Passel.WebApi.IntegrationTests/Invex.Passel.WebApi.IntegrationTests.csproj

dotnet atom TestWebApi runs it after the unit tests, and so do the Validate and Build workflows, since GitHub-hosted runners have Docker.

The suite starts one postgres:18.3 container and one azurite:3.35.0 container (the images the AppHost runs) with Testcontainers and hosts the API in-process with WebApplicationFactory, pointed at them through the passel-db and passel-blobs connection strings. Azurite is started with --skipApiVersionCheck, because the storage SDK asks for a newer service version than that Azurite knows of (the AppHost's emulator passes the same flag). The extra hosts that some tests build on databases of their own (the empty database, the migration tests, storage being down) are given an in-memory blob store, or one that always fails, instead, and one is given the filesystem store over a temp directory, to take an upload, its download, its thumbnail and its erasure through the API on that store. The file limits are lowered for the run (1 MB a file, 3 MB and five unsent files a user) so the quota tests upload little, and the sweep's worker is off: the tests run the sweep themselves, passing it a time an hour or more ahead to expire files without waiting, apart from one test that turns the worker on and checks that a deleted file is erased within seconds. Requests are signed in with the Development Authorization: Dev <user> scheme, and every test acts as users of its own, so the tests share one database without seeing each other's packets. The rate limits are raised for the run, because paging alone creates 51 packets in a minute; the limits have unit tests of their own. Before the first test, the fixture creates packets until one arrives on an event stream, because the notification listener connects after the host has started and a packet created before then is announced to nobody.

The tests speak HTTP only, as the clients do: they assert the JSON and the events, never tables or Marten types, apart from the privilege checks of the migration test and the file tests that run the sweep, read the blob store or write a parcel's document directly to set up a race. They cover creating and listing with ownership isolation, paging over 51 packets through the cursor, the delete semantics (a second delete and another user's packet are both 404), the event stream end to end (a create and a delete committed through the API arrive as packet-created and packet-deleted on the owner's stream, through the database notification, and on nobody else's), link previews (the file names made safe, the size limit with and without a length, the storage quota and the unsent-file limit, the File packet listed and announced, a file sent only once, including two sends at the Contracts

Packets have one wire shape, PacketEndpoints.PacketResponse (Endpoints/PacketEndpoints/PacketResponse.cs): a GET /api/packets item, the POST /api/packets response and the packet-created and packet-updated event data are all this type, built from the stored Packet document by PacketResponse.From, the only mapper. The request body (PostPacketRequestBody) stays a type of its own, because a packet has no id and no creation time before it is stored, and the PacketContent union in Domain/Packet.cs is the storage shape, not the wire. Each endpoint declares its responses, so the OpenAPI document carries the shapes and the problem responses.

The contracts/ folder at the repository root holds what the API puts on the wire, and the integration tests (ContractTests) keep it true:

  • contracts/openapi.json is the document the Development host serves at /openapi/v1.json, which is why it declares the Dev scheme next to the bearer token, minus the servers entry, which names whatever address served the copy. The test fails when the committed document differs from the served one.
  • contracts/fixtures/ holds a list page with every packet type (the link with its preview), a create response, a packet-created, a packet-updated and a packet-deleted event payload, serialized from fixed packets with the host's real JsonOptions (indented, with LF line endings, which the clients never see). One test fails when a committed fixture differs from what the API serializes now, another when an endpoint answers with properties other than its fixture's, and the extension and mobile app suites parse every fixture with their real parsers.
  • contracts/feed-scenarios.json describes feed sequences and the list each must leave behind; both client suites run them through their feed stores, and the API tests check that every packet in the file is a valid wire packet.

The device and parcel endpoints are in contracts/openapi.json but have no fixtures yet: the fixtures are for payloads the client suites parse, and no client calls them until roadmap 2.D3 and 2.E2 (devices) and 2.C2, 2.D2 and 2.E2 (files), which add the fixtures and their checks together. Both client suites fail on a fixture they have no check for. The File packet is covered all the same: the shape test uploads an image, sends it, and compares the listed File item with the one in the list-page fixture, and the upload response's property set is checked in the file tests.

To regenerate the document and the fixtures after a change, run the integration tests with PASSEL_UPDATE_CONTRACTS=1 set, review the diff and commit it with the change; see Contracts in the testing guide.
