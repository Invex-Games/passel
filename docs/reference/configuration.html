Parameter Secret Passed to

google-client-secret Yes The API's Authentication:Google:ClientSecret
google-extension-client-id No The API's Authentication:Google:AdditionalAudiences:0, and the extension's GOOGLE_CLIENT_ID

The values are stored in the AppHost's user secrets as Parameters:<name>. In Development all three are optional and default to empty, so the dashboard doesn't prompt for them; the API then works through the Dev scheme described in Run without Google. Outside Development they're required. google-client-secret is only used locally: a published or deployed AppHost never asks for it, and the API in Azure never has it. The AppHost also gives the extension and the web app API_URL (<API https endpoint>/api/packets), runs the web app on PORT 5245, and gives the API its passel-db connection string, the passel-blobs connection string of the passel-storage resource (Azurite, in a persistent container with a data volume, so stored files survive AppHost restarts as the database does) and the web app's origin, http://localhost:5245, as Cors:AllowedOrigins:0. The API waits for the parcels container to exist before it starts.

The AppHost reads one setting of its own:

Key Default Description
DevTunnel:AllowAnonymous true Whether the passel-api-tunnel resource lets anyone with the URL through. Set it to false (in user secrets, the git-ignored appsettings.Development.json, or the DevTunnel__AllowAnonymous environment variable) and the tunnel requires a Dev Tunnels access token, which the mobile app sends from TUNNEL_ACCESS_TOKEN; see Requiring a token. The tunnel only runs when started from the dashboard either way.

Compose deployment

The self-hosted deployment (Releasing and Deploying) reads every value from the server's /opt/passel/.env, whose template, with a comment on each key, is deploy/compose/.env.example; release.env, written by deploy.sh, adds PASSEL_TAG. compose.yaml gives the API, db-migrate and the web app an explicit environment built from those keys, never the whole file, so nothing else in .env reaches them.

.env key Required Becomes
PASSEL_TAG Set by deploy.sh The tag of the passel-webapi and passel-web images, and service.version in OTEL_RESOURCE_ATTRIBUTES
COMPOSE_FILE, COMPOSE_PROFILES Yes Which files and profiles every compose command uses: the proxy setup, and telemetry for the dashboard
POSTGRES_USER, POSTGRES_DB No The superuser and the database PostgreSQL creates on first start (postgres, passel); POSTGRES_DB is also the database in both connection strings
POSTGRES_PASSWORD Yes The superuser's password, which db-roles signs in with. PostgreSQL only sets it when the database is first created
PASSEL_OWNER_DB_PASSWORD Yes The password of passel_owner, and db-migrate's ConnectionStrings__passel-db (Username=passel_owner)
PASSEL_API_DB_PASSWORD Yes The password of passel_api, and the API's ConnectionStrings__passel-db (Username=passel_api). db-migrate gets Database__ApiRole=passel_api
ENCODING_ALPHABET Yes Encoding__Alphabet. Never changed once ids are in use
GOOGLE_WEB_CLIENT_ID Yes Authentication__Google__ClientId, and the web app's GOOGLE_CLIENT_ID, which it signs in with
CHROME_EXTENSION_CLIENT_ID No Authentication__Google__AdditionalAudiences__0
API_HOST Yes AllowedHosts, as <API_HOST>;localhost (the healthcheck sends localhost); the web app's API_ORIGIN, https://<API_HOST>, which it calls and allows in its policy; the edge's site for the API; the smoke check's default https://<API_HOST>/health

PROXY_NETWORK With compose.external-proxy.yaml The existing Docker network the edge network becomes

The compose file also sets, on the API and db-migrate, ASPNETCORE_ENVIRONMENT and DOTNET_ENVIRONMENT to Production, and on the API Parcels__Store=FileSystem with Parcels__FileSystemRoot=/var/lib/passel/parcels, in the parcels volume. To tune one of the Web API settings below on the server, add it to the API's environment in a compose override kept outside the releases, such as /opt/passel/compose.local.yaml, and add that file to COMPOSE_FILE by its absolute path (COMPOSE_FILE=compose.yaml:/opt/passel/compose.local.yaml); the release directories are replaced on every deploy.

These stay unset in the compose deployment, since each belongs to Azure or to Development and would change how the API signs in, exports or trusts headers: APPLICATIONINSIGHTS_CONNECTION_STRING, every AZURE_* variable, Database__ApiRoleObjectId, Authentication__Google__ClientSecret and ASPNETCORE_FORWARDEDHEADERS_ENABLED.

Outside Development, appsettings.Production.json keeps Npgsql's log of every command it runs to warnings, so production logs don't carry each SQL statement.

Link previews are fetched after a link is created, behind guards that no setting loosens: http and https only, public addresses only, checked on every redirect. See Link previews.

CORS is for the web app alone: the extension's host permissions bypass CORS, and the mobile app isn't a browser. An origin in Cors:AllowedOrigins may call the API with GET, POST and DELETE, sending Authorization, Content-Type and Accept, and Range and If-None-Match to resume or revalidate a file download, and may read Retry-After, Location, ETag, Content-Disposition, Content-Range, Accept-Ranges and Content-Length; credentials (cookies) are never allowed, since the clients send a bearer token. Preflight requests are answered ahead of authentication and rate limiting. Any other origin gets no CORS headers, so the browser keeps the answer from its page. Outside Development the API also sends HSTS.

Rate limits are sliding one-minute windows counted per signed-in user (the sub claim), or per remote address for requests that aren't authenticated. A request over the limit gets a 429 problem with a Retry-After header.

Quotas are checked before every create with one indexed aggregate over the user's packets. The byte quota counts the stored size of the packet documents, which PostgreSQL compresses when they're large, so it's a storage cap rather than an exact character count. A user at the packet limit gets a 429 problem; a packet that would pass the byte limit gets a 413 problem. Both say to delete packets. The device cap is checked only when an installation registers for the first time, so a device that is registered already is never refused; a user at the cap gets a 429 problem saying to remove a device. New installations registering at the same moment are all checked against the same count, so a burst can pass the cap by up to RateLimits:DeviceWritesPerMinute less one; raising that limit loosens the cap too. Lowering the cap removes nobody's devices.

Uploads are checked against their own quotas, before the body is read and again once the file is stored: a file over Parcels:MaxParcelBytes or one that would pass Quotas:MaxParcelBytesPerUser gets a 413 problem, and an upload beyond Quotas:MaxPendingParcelsPerUser unsent files a 429 problem. Lowering a limit deletes no files. The upload endpoint sets the request body limit of its own requests to Parcels:MaxParcelBytes plus 64 KB for the multipart framing, and counts the file itself as it reads it. When the file limit is set above Kestrel's default of about 30 MB, raise Kestrel:Limits:MaxRequestBodySize with it; only the endpoint's own count is covered by the tests, because the test server enforces no body limit.

When you run the API outside the AppHost, put these in src/webapi/Invex.Passel.WebApi/appsettings.Development.json. The file is git-ignored by the *.Development.json rule. Settings supplied by the AppHost take precedence over the file.
