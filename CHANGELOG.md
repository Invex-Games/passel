# Changelog

All notable changes to Passel. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versions come from [GitVersion](GitVersion.yml) and conventional commits. Nothing has been released yet.

## Unreleased

### Added

- The Android app is a share target: "Send to Passel" appears in the share sheet for text and links and in the text selection menu, and opens the send sheet filled in. The extension's screens use the same Send, link and note wording as the app.
- Real-time packet updates: the API streams server-sent events backed by PostgreSQL notifications, and the mobile app and extension keep a live connection open while visible.
- Deleting packets, with a four-second undo, in the mobile app and the extension; deletions are announced live.
- The extension popup shows the packet feed, with paging, caching and copy actions.
- An Aspire AppHost that runs PostgreSQL, the API, the extension's watch build and a dev tunnel for phones, prompting for the Google OAuth values.
- Build targets for the test suites and for checking and preparing a development machine (`SetupDevEnvironment`).
- A DocFX developer site under `docs/`, with an October 2026 evaluation of the project, a feature list, a web app plan and a roadmap.
- GitHub Actions workflows and Dependabot configuration generated from the Atom build definition, plus contributing guidelines, code owners, a pull request template and the MIT license.
- Abuse controls in the API: rate limits per user for creates, reads and event streams, per-user packet and storage quotas, caps on open event streams per user and per instance, and streams that end when the token they were opened with expires.
- A Development-only `Authorization: Dev <user>` scheme, so the API, Scalar and the tests run without Google credentials; the AppHost's Google parameters are optional in Development. Scalar opens with the scheme filled in for a visitor who is not logged in with Google, and otherwise selects the Google login, which the document declares as its own scheme.
- Sign-in without Google in the clients' development builds: the mobile app's `DEV_USER` dart-define and the extension's `DEV_SIGN_IN` build flag (set by the AppHost) sign in through that scheme as any named user, with a field for switching users, so per-user behaviour can be tested from one device. Production builds refuse the define and never compile the flag in.
- A USB path for mobile development: the development flavor of the app may use plain HTTP to `localhost` and the emulator host, so a phone reaches the local API through `adb reverse` without a tunnel; the production flavor refuses an `http://` API URL. A `TUNNEL_ACCESS_TOKEN` dart-define and a `DevTunnel:AllowAnonymous` AppHost setting for running the dev tunnel without anonymous access.
- Integration tests for the API against PostgreSQL in Docker (Testcontainers): ownership isolation, paging, delete semantics, live updates end to end and the schema on an empty database. `dotnet atom TestWebApi` and the workflows run them after the unit tests.
- Widget tests for the mobile app's screens: the feed page signed in and out with its sync label, the list's loading, failure and empty states and its loading of older items, the send sheet, the tiles and delete with undo. `dotnet atom TestMobileApp` runs the suite with coverage and keeps the lcov report as a build artifact.
- One wire shape for packets in the API, shared by the list, the create response and the `packet-created` event, with the OpenAPI document and sample payloads committed under `contracts/` and checked against the running API, and feed scenarios that the extension and mobile app test suites both run, so the three sides can't drift apart unnoticed.
- A settings page in the mobile app, opened from the feed's app bar: the signed-in account with Sign out (or Sign in), a theme choice of system, light or dark that is kept across restarts, the app version and build number, and the privacy policy and terms links, disabled until those pages exist.
- Link previews: after a link is sent, the API fetches its page in the background (`http` and `https` only, public addresses only, checked on every redirect, with caps on time and size) and attaches the page's title, description and image to the link as its `preview`, announced live as a `packet-updated` event. The extension and the mobile app ignore the field and the event until their tiles show previews.
- Deployment of the API to Azure (ADR 0003, proposed until the owner confirms the subscription): Azure Container Apps, Azure Database for PostgreSQL flexible server with 14 days of point-in-time restore, Key Vault for the Sqids alphabet, and Application Insights, all modelled in the AppHost and deployed with `aspire deploy` by a manual `Deploy` workflow that signs in to Azure with OIDC (`dotnet atom DeployWebApi`). Every pull request writes the generated Bicep (`PublishAzureInfrastructure`). The local run and the tests are unchanged, and nothing deploys until the one-off setup in the deploying guide is done.
- The API sends its logs, traces and metrics to Application Insights when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set, and signs in to PostgreSQL with a Microsoft Entra token for its managed identity when the connection string has no password. The link preview fetcher's requests are left out of the traces, outgoing HTTP and DNS metrics carry no host name, and the reason a link got no preview is logged at Debug, so the links users send don't reach the telemetry.
- A device registry in the API (`/api/devices`), ready for push notifications: clients register each installation (idempotently, by an installation id they generate once), list, rename and remove their devices, and give each device a push token (an FCM token on Android, a Web Push subscription in a browser). A token is never returned or logged, and belongs to one device at a time: the same token registered by another account moves to it. Users may have 20 devices (`Quotas:MaxDevicesPerUser`), and device writes have a rate limit of their own (`RateLimits:DeviceWritesPerMinute`). Registrations of one installation sent at the same moment all get its one device, and a device change that keeps colliding with others on the same device gets a 409 problem saying to send it again. The clients do not register yet.
- The web app (roadmap 1.E2), at `src/web` in the npm workspace: sign in with Google, or as a development user in a development build, and see your feed newest first, loading older items as you scroll and staying live while the tab is visible (and for a minute after it is hidden, so switching tabs opens no new stream), with link previews arriving as their pages are read. When the hourly Google session runs out it says so and offers One Tap. The AppHost serves it at `http://localhost:5245` (`web-app`), and `dotnet atom BuildWebApp` builds the static site into `atom-publish/WebApp`; nothing deploys it yet. The Google web client needs `http://localhost` and `http://localhost:5245` as Authorized JavaScript origins.
- A landing page and privacy and terms pages in the web app (roadmap 1.E3), plain HTML with no script, each linking to the documentation. The privacy policy and terms describe what Passel stores and does today and are drafts pending legal review, with the facts still to be supplied marked as placeholders.
- A CORS policy for the web app: `Cors:AllowedOrigins` lists the origins allowed to call the API from a browser (none by default; the AppHost sets the web app's), with no credentials, and the API refuses to start with an origin written any other way than a browser sends it.
- `@passel/core` applies `packet-updated` events (a listed item is replaced in place, never added), parses link previews, and gains a `fetch`-based API client, a reconnecting event stream and ID token helpers for the web app.
- Unit tests for the extension's own modules, against a stubbed `chrome` with jsdom for the popup: sign-in, the API client's 401 handling and error messages, the live connection's backoff, the service worker's delete scheduling, context menus, keyboard commands and the address bar keyword, and the side panel. `dotnet atom TestChromeExtension` runs the workspace's tests with coverage and keeps the lcov reports as a build artifact, like the mobile app's.
- The extension has a side panel, keyboard shortcuts and an address bar keyword. The side panel is the popup's feed and composer laid out for a tall panel that stays open beside the page; open it from the popup's header, with Alt+Shift+O or from Chrome's side panel menu. Alt+Shift+P opens the popup and Alt+Shift+S (Alt+Shift+Y on ChromeOS) sends the page you're on, or the text selected on it, without opening anything (Control instead of Alt on a Mac). Typing `passel`, a space and some text in the address bar sends it as a note, or as a link if it's a web address. A sign-in or sign-out from the popup, a shortcut, the keyword or a context menu shows at once in an open side panel, which then shows only the new account's feed. The extension asks for two new permissions without install warnings, `sidePanel` and `scripting`. The side panel asks for the optional `tabs` permission the first time it sends a page. If you decline, it doesn't ask again unless you choose Allow in the message it shows when it can't read a tab. It now needs Chrome 116.
- Parcels (roadmap 1.B3): `POST /api/parcels` uploads a file as `multipart/form-data` (one part named `file`), streamed to Azure Blob Storage with its type sniffed from its bytes and, for a JPEG, PNG, GIF or WebP image, its size and a 512 px WebP thumbnail with no metadata; a File packet then sends it by `parcelId`, once. `GET /api/parcels/{id}` downloads it byte for byte with a strong `ETag`, ranges and immutable private caching, inline only for images and PDFs and always under `Content-Security-Policy: sandbox` and `nosniff`; `/thumbnail` returns the thumbnail; `DELETE /api/parcels/{id}` discards a file not yet sent. Deleting a File packet deletes its file, and a sweep erases deleted files within seconds (soft delete and versioning are off on the storage account), deletes files left unsent for an hour, and once a day removes stored bytes with no file. A file may be at most 25 MB (`Parcels:MaxParcelBytes`), a user's files 500 MB together (`Quotas:MaxParcelBytesPerUser`), and a user may have 20 files unsent (`Quotas:MaxPendingParcelsPerUser`); uploads and reads have rate limits of their own (`RateLimits:ParcelUploadsPerMinute`, `RateLimits:ParcelReadsPerMinute`). Storage being down answers 503 on the file endpoints and leaves `/health` and everything else working. The AppHost runs Azurite for it (`passel-storage`, persistent), the Azure deployment adds a storage account with Storage Blob Data Contributor for the API alone, and the integration tests run against Azurite. The clients do not upload or show files yet (2.C2, 2.D2, 2.E2).

### Changed

- The File body of `POST /api/packets` takes `parcelId` and an optional `fileName` in place of the unused `contentType` and `payload`, and gets 400 on `parcelId` for a file the caller can't send and 409 for one already sent; CORS now allows `Range` and `If-None-Match` and exposes `ETag`, `Content-Disposition`, `Content-Range`, `Accept-Ranges`, `Content-Length` and `Location`. `Quotas:MaxBytesPerUser` counts packet documents only, as before; uploaded files have their own quota.
- Outside Development the API no longer creates or changes the database schema (roadmap 0.A3): a migration job runs the API's new `db-migrate` command before each release, applying the schema and granting the API's database role only DML, and the API refuses to start on a schema that lacks a table, column or function it needs. It accepts what a newer release's migration added, so the previous release can still restart if a deployment fails after its migration. The migration never drops a column, index or foreign key, so a rollback keeps what a newer release added and the data in it. Development still applies the schema at startup. Marten 9 generates no code at runtime, so no `codegen write` step is needed.
- Npgsql's log of every command is kept to warnings in Production.
- The TypeScript code is an npm workspace at `src/` (roadmap 1.E1): `@passel/core` holds the platform-free client logic (wire types and parsing, the feed store, the server-sent events parser, the authorization header) with its tests and the contract checks, `@passel/ui` holds the design tokens, and the extension consumes both, so the web app can share them. The popup script is split into a controller, a feed view, a composer and the toast, and a popup harness serves the built popup with `chrome.*` stubbed (`npm run harness`).
- The mobile feed shows the newest item at the top like the extension, with pull-to-refresh at the top and older items loading at the bottom, and its screens say "Send" and speak of links, notes and files rather than packets (ADR 0002, which also settles the web app stack, the parcel store and the hosting).
- Packets are plain Marten documents instead of event streams with a snapshot (ADR 0001): a delete erases the packet, each packet is stored once, and the list and create responses and the `packet-created` event carry `createdAt`. A development database from before keeps its old tables, which can be dropped.
- Marten 9 and current Aspire, OpenTelemetry and Google packages.
- Line endings are LF everywhere, files carry no byte-order mark, and the Atom build tool is pinned in `dotnet-tools.json`.
- NuGet package versions are managed centrally in `Directory.Packages.props`; the .NET SDK is pinned in `global.json`.
- The extension tests run on vitest 5; the unused `cupertino_icons` dependency and the unused file-packet command and endpoint helpers were removed.
- HTTP hygiene in the API: CORS is off until the web app needs it, HSTS and host filtering apply outside Development, forwarded headers are honoured behind a setting, the development cookies and OIDC nonce validation are hardened, and the Aspire dashboard asks for its login token.
- The dev tunnel no longer starts with the AppHost; start it from the dashboard when a phone is not on USB. Scalar, the OpenAPI document and the browser login answer only on `localhost`, so they are never served through the tunnel.
- The extension caches only the first page of the feed, lays the feed out in one pass and animates only packets that arrive live, shows every piece of feedback in one snackbar, hides the composer while signed out, truncates long tab titles, caps its event-stream buffer, and spreads reconnects and resync fetches.
- The mobile app caches only the first page with debounced writes and a single parse, shows the cached feed before Google Sign-In has initialised, keeps tile state across inserts, clamps long notes to eight lines with a "Show more" toggle, spreads reconnects and resync fetches, and keeps its app bar while the feed is pulled to refresh, with the empty feed saying which way to pull. A cold start without a cache shows the feed's spinner, or its failure row, while the first fetch runs rather than an empty feed.
- Query and live-update tuning in the API: the feed is served by one composite index on user and packet id (with the DDL and measured plans in the Web API docs), live updates are dispatched in batches with one query per batch, stream heartbeats are timed without exceptions, event streams are left out of request tracing, resyncs after a listener reconnect are spread over a few seconds, and each stream sends its own `retry` value.
- The mobile app runs on Riverpod 3 (`flutter_riverpod` 3.3) and `share_plus` 13, with its providers opted out of the automatic retry Riverpod 3 adds so failures still surface at once; `dynamic_color` stays on 1.x until the Flutter SDK ships Dart 3.12.

### Fixed

- A request body the API cannot read (an unknown `$type`, a missing required field) gets a 400 problem in Development too, as in production, rather than a 500. So does a packet or a push token without its `$type`, which got a 500 in every environment.
- Packets are scoped to their owner on every endpoint, and ids cannot be probed.
- Notifications are sent only after the database commit, so a rolled-back packet is never announced.
- The extension routes every API call through its service worker and keeps the ID token in session storage.
- The mobile app refreshes tokens, clears user data on sign-out and account change, and no longer races its feed updates.
- The mobile app shows readable messages for API, network and sign-in failures instead of raw exception text.
- Build fixes: the extension is built against its packets endpoint, the pub cache survives Flutter builds, and tools are found on any OS.
